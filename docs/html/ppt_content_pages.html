과제 배경 1: 외부 LLM을 그대로 쓰기 어려운 이유

보안과 지식재산권, 사내 코드 지식 부족, Fine-tuning 부담

02

보안/IP 보호

  • 사내 코드는 핵심 자산

과제 배경 3: 일반 문서 RAG와 코드 어시스트 RAG의 관심사

일반 문서 RAG의 주요 관심사와 코드 어시스트 RAG의 Architecture Driver는 다르다

04

일반 문서용 RAG에서 주로 중요한 것

  • 문서 의미 검색: 질문과 가까운 단락을 찾는 능력
  • 요약 품질: 긴 문서를 이해하기 쉬운 답변으로 압축
  • 출처 인용: 어떤 문서에 근거했는지 확인
  • 최신 문서 반영: 오래된 정책/FAQ 사용 방지
  • 질문 의도 파악: 필요한 문서 범위 선택

코드 어시스트 RAG에서 강해지는 Driver

  • 중복성: 유사 코드가 Top-K를 잠식
  • 권한 민감성: Repository/Project/보안 모듈별 접근 제한
  • 최신성/버전: Branch/Release/Commit마다 정답이 다름
  • 정확도: API Signature와 호출 순서 오류가 실제 장애로 연결
  • 응답 속도: IDE 흐름 안에서 짧은 지연 필요
  • 근거 추적: File/Symbol/Segment/Commit/Citation 필요
코드 어시스트 Driver왜 중요한가연결 DP
중복성복사 구현, 샘플 코드, 버전별 유사 파일이 Top-K를 잠식하면 필요한 근거가 누락된다.DP1
권한 민감성권한 없는 코드가 답변이나 로그에 섞이면 보안 사고가 된다.DP2
최신성/버전요청 Branch/Release/Commit과 다른 구현은 틀린 답변이 될 수 있다.DP2, DP3
정확도/응답 속도틀린 코드 제안은 빌드/런타임 오류로 이어지고, 느린 응답은 개발 흐름을 끊는다.DP1, DP3
근거 추적답변 근거의 파일, Symbol, Segment, Commit, 권한 판단을 확인할 수 있어야 한다.DP1, DP2, DP3
핵심 메시지: 코드 어시스트 RAG는 일반 문서 RAG의 검색/요약 문제 위에 중복, 권한, 버전, 실행 정확도, 근거 추적 문제가 추가된다.

DP1의 출발점은 “RAG를 쓴다”가 아니라 “중복이 많은 코드 Corpus에서 검색 근거의 다양성과 신뢰성을 어떻게 유지할 것인가”이다. 같은 API 구현이 여러 Repository, Branch, 샘플 코드, Legacy 코드에 반복되면 Top-K가 비슷한 Chunk로 채워지고, LLM은 최신 구현이나 주의사항 같은 보완 근거를 놓칠 수 있다.

설계 질문

중복이 많은 코드 데이터에서 Top-K 편향과 Hallucination을 줄이기 위해 어떤 RAG 구조를 사용할 것인가?

중복 강건성Prompt 감소Citation

중복은 품질 문제이면서 비용 문제다. 같은 의미의 Chunk가 반복 투입되면 Prompt Token, Reranking 비용, 생성 지연이 함께 증가한다.
예상 발표 스크립트: 사내 코드베이스는 일반 문서보다 중복이 훨씬 많이 발생합니다. 같은 기능이 여러 프로젝트에 복사되어 있거나, 버전별로 거의 같은 파일이 남아 있거나, 샘플 코드와 실제 운영 코드가 함께 검색될 수 있습니다. 이런 상태에서 단순 Top-K 검색을 하면 검색 결과가 모두 비슷한 코드 조각으로 채워질 수 있고, LLM은 충분히 다양한 근거를 보지 못합니다. 오래된 구현이나 샘플 코드를 최신 권장 구현으로 오인하면 코드 어시스트의 신뢰도도 크게 떨어집니다. 그래서 DP1은 중복이 많은 코드 환경에서 검색 근거를 어떻게 다양하고 대표성 있게 구성할지 결정하는 지점입니다.

DP3 대안 비교: Verified Answer Cache vs Incremental Context Cache

선택안은 증분 가능한 Context Cache

16

A. Verified Answer Cache

flowchart TD Q[User Query]-->P{Answerable Question Pool?} P-->|No|R[Full RAG + LLM] P-->|Yes|E[Query Embedding] E-->C[Answer Cache Lookup] C-->H{Cache Hit?} H-->|No|R H-->|Yes|V{Metadata Valid?} V-->|Yes|A[Cached Final Answer] V-->|No|R R-->S[Store Answer Cache]

핵심: FAQ/API 기본 사용법처럼 답변이 명확한 질문에 한해 검증된 최종 답변을 재사용한다.

장점: hit 시 RAG와 LLM을 모두 생략하므로 가장 빠르다.

단점: 사용처가 제한되고, 비슷하지만 다른 질문에 wrong answer reuse 위험이 있다.

B. Incremental Context Cache

flowchart TD Q[User Query]-->E[Query Embedding] E-->C[Context Cache Lookup] C-->H{Cache Hit?} H-->|No|R[Full RAG] H-->|Yes|V{EU-level Validation} V-->|All Valid|P[Cached Context Pack] V-->|Partial Invalid|D[Delta Retrieval] V-->|Many Invalid|R D-->B[Context Pack Rebuild] R-->B B-->U[Update Context Cache] P-->L[LLM Answer] U-->L

핵심: 최종 답변은 재사용하지 않고, RAG가 반환한 Context Pack을 EU 단위로 검증해 LLM에 전달한다.

장점: 질문 범위 제약이 작고, 질문 뉘앙스를 반영할 수 있으며, 일부 invalid EU는 delta retrieval로 보강한다.

단점: LLM 호출은 남고, validation/delta retrieval 정책이 복잡하다.

예상 발표 스크립트: 검증형 답변 캐시는 hit 이후 가장 빠르지만, 답변이 명확한 질문에 제한적으로 적용해야 합니다. 반면 증분 가능한 Context Cache는 LLM을 반드시 통과하므로 속도 절감은 제한적이지만, 질문 대상에 대한 제약이 작고 현재 질문의 뉘앙스를 반영할 수 있습니다. 또한 일부 EU만 invalid한 경우 전체를 버리지 않고 delta retrieval로 보강할 수 있습니다.
