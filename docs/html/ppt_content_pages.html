사내 코드 보안, 권한 정합성, 중복 데이터 강건성, 응답 속도를 동시에 다루는 설계 과제

01

핵심 한 줄

외부 LLM에 사내 코드를 보내지 않고, 내부 RAG 지식 계층으로 코드 어시스트 품질을 확보한다.

3개 Design Point

DP1 SPRAG/EUDP2 PermissionDP3 Knowledge Cache

발표 Tone

실제 구현 완료가 아니라 Architecture 판단과 Trade-off를 설명하는 설계 발표다.

발표자 노트: 첫 장에서는 “코드 어시스트를 만들겠다”보다 “사내 코드라는 제약 때문에 일반 LLM 도구를 그대로 쓸 수 없고, 내부 검색/권한/근거 계층이 필요하다”를 먼저 말한다.

과제 배경 1: 외부 LLM을 그대로 쓰기 어려운 이유

보안과 지식재산권, 사내 코드 지식 부족, Fine-tuning 부담

02

보안/IP 보호

  • 사내 코드는 핵심 자산
  • 외부 LLM 전송 시 정책 위반 위험
  • 질의/로그/Context까지 통제 필요

사내 지식 부족

  • 외부 모델은 내부 API/프레임워크를 모름
  • 프로젝트별 규칙과 설계 제약 미반영
  • 그럴듯하지만 틀린 답변 위험

모델 개발 부담

  • 전용 모델 학습 비용 큼
  • 코드 변경 시 재학습 부담
  • 지식을 파라미터에 고정하면 최신성 불리

과제 배경 3: 왜 RAG 중심 설계인가

모델 재학습보다 최신 사내 지식을 검색 계층으로 제공하는 접근

04

Fine-tuning 중심 접근의 부담

  • 데이터 구축/학습/배포 비용 큼
  • 코드 변경 때마다 최신성 보장 어려움
  • 권한별 지식 차이를 모델 파라미터에 반영하기 어려움

RAG 중심 접근의 장점

  • 모델은 범용으로 유지
  • 코드/문서는 검색 계층에서 최신화
  • 권한, 중복, Citation을 Architecture로 통제

DP1 대안 비교: Naive RAG vs RAPTOR vs SPRAG EU

선택안은 SPRAG 기반 Evidence Unit Offline Dedup-aware RAG

flowchart TD A[Docs]-->B[Chunking]-->C[Embedding]-->D[Top-K]-->E[LLM]

장점: 단순, 빠른 PoC, 운영 복잡도 낮음

단점: 중복 코드에 취약, Top-K 편향, Token 낭비

B. RAPTOR-style

flowchart TD A[Chunks]-->B[Cluster]-->C[Summary Node]-->D[Hierarchical Search]-->E[LLM]

DP2 배경: 권한 기반 Dataset / Retrieval Strategy

정확한 검색도 권한이 맞지 않으면 사용할 수 없다

상황위험필요한 Architecture 대응
